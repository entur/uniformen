# Uniformen

TypeScript service on Bun and Hono that server-renders the header and footer every
Entur B2B application embeds, plus the `@entur/uniformen` client package that fetches
and mounts them.

## Conventions

- Commit subjects for the service carry the Jira key where there is one, then the
  description in the imperative: `ETU-76720 add new param loginUrl which renders the
  "Logg inn" button`.
- A change under `packages/uniformen/` uses a Conventional Commits subject instead,
  because release-please reads it to decide the package's next version:
  `feat(uniformen): add loginUrl to the render options`. Types: `feat` (minor),
  `fix` (patch), `feat!` or a `BREAKING CHANGE:` footer (major), and `chore`, `docs`,
  `refactor`, `test`, `build`, `ci` for anything that ships no user-visible change.
  Put the Jira key in the body, not the subject. `Verify PR` enforces this on any pull
  request touching the package; pull requests that leave the package alone are not
  checked.
- Keep a pull request on one side of that line. On a squash merge the pull request
  lands under a single subject, so a `feat(uniformen):` title releases the package
  even when most of the diff is service code. Two traps: a **single-commit** squash
  uses the *commit* subject rather than the pull request title, and the squash body
  carries every intermediate commit message — so a stray `BREAKING CHANGE:` footer
  cuts a major release. Merge and rebase are also enabled, and there each commit
  subject lands as it is.
- Dependencies are pinned exactly; `bunfig.toml` also refuses any package version
  published less than three days ago. Do not loosen either.
- User-visible render changes go in `CHANGELOG.md`, written by hand and dated.
  `packages/uniformen/CHANGELOG.md` is generated by release-please from commit
  subjects — do not edit it, and do not bump `version` in the package's
  `package.json` by hand either.
- A new or changed query parameter must land in three places: the handler, the README
  parameter table, and the preview page's controls.
- Applications in `src/components/portalApplications.ts` are declared in the order the
  switcher lists them — alphabetical by Norwegian collation, Ø last.

## Critical Rules

- Everything committed here is world-readable, including commit messages and git
  history. Do **not** write internal-only material into the repository: Confluence or
  Jira links, internal runbooks, customer names, or anything about Entur systems a
  reader outside Entur should not have. A Jira key in a commit subject is fine; the
  ticket's contents are not.
- Do **not** commit secrets. Runtime secrets come from Secret Manager via the Helm
  chart; `.env` is git-ignored and `.env.example` holds only public OIDC endpoints.
- Do **not** add third-party font, image, or icon assets. Licensing of bundled assets
  is the open-sourcing constraint for this repository.
- The `/ssr` endpoint is public and treats its token as optional enrichment — an
  invalid or missing token renders the anonymous bar rather than failing. Keep that
  behaviour; do not turn it into an authorization check.
- `loginUrl` and `logoutUrl` accept only a path on the app's own origin. Absolute
  URLs, `//host`, and `javascript:` are rejected with a 400. This is open-redirect
  protection, keep it strict.
